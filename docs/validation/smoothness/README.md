# 手势驱动连续性优化

本轮针对“画面不卡顿，但移动食指时水墨不够丝滑”。保留 Gain 24、原模拟网格、颜色精度及恢复参数。没有保存摄像头影像或关键点。

## 原因与修改

真实 Interaction 控制器的恒速回放表明，20 Hz 输入配合 60 Hz 渲染时，原来约 67.8% 渲染帧没有新增受力，单帧推动峰值约为均值的 3.1 倍。仅将输入改为 30 Hz，仍约有 50.8% 空档帧。

新增 MotionResampler，在后续渲染帧中逐步消耗每段已确认位移；没有预测未发生的运动，也不会重复放大总推动。手势失效、控制手切换、重置立即丢弃尚未消耗的位移。静止后有限尾段结束，不持续施力。

识别结果携带采集时间，避免传输时延波动被误算为手移动速度；识别调度保留周期余量，避免 20 FPS 目标在 30 FPS 预览时钟下退化为 15 FPS。推理同时最多一个任务，通信只保留一个在途结果和一个可替换的最新结果，不堆积旧帧。

新增回归测试还复现了快速移动时的坐标不一致：位移被限速，位置却直接跳到未限速坐标。修复后，两者沿相同路径更新，避免补帧从错误位置开始。微小于死区的位移不再单独挪动受力坐标。

## 对照与现场反馈

| 记录 | 渲染 FPS | 实际识别 FPS | 移动期空档帧：原输入 → 连续受力 |
| --- | ---: | ---: | ---: |
| `20fps-first-accepted.json` | 59.94 | 14.59 | 75.4% → 0.09% |
| `30fps.json` | 60.00 | 16.50 | 72.1% → 0.31% |
| `20fps-final.json` | 55.82 | 15.33 | 74.0% → 0.08% |

每轮为 3 秒预热后约 35 秒直接逐帧计时，真实摄像头和真实控制器，预览默认打开。移动期统计限定有效手势且最近 80 ms 内出现过位移；该指标用于检验输入连续性，不能代替视觉验收或端到端延迟测量。最后一轮开发进程采样没有达到 60 FPS，保留原始结果，不将它作为性能达标证据。

用户首先确认 20 FPS 连续受力版本“明显更顺滑”。随后摄像头实际协商为 30 FPS、识别目标 30 FPS，用户反馈“没有卡顿，但是不如刚刚跟手”，摄像头标记及山水受力位置均会跳变。因此退回 20 FPS，保留连续受力，修复坐标与限速路径一致性；不能把 30 FPS 目标写作实际达到的识别帧率。

最终现场验收：用户按匀速画圆、快速转向、停住食指的步骤，确认恢复 20 FPS 后“更跟手，跳变已不明显”。交付工程重新加载后的 45 秒观察见 `delivery-performance.json`：45 次滚动 600 帧状态采样，滚动 FPS 均值 59.75、最低 59.10，最大滚动 P95 帧间隔 20.77 ms，17 次采样有有效交互，所有采样摄像头 ready、节点无错误。该值是重叠窗口统计，不是独立逐帧全程平均，也不替代长时间稳定性验收。

`30fps-before-worker-scheduling.json`、`30fps-idle-worker-scheduling.json` 主要为空闲对照，不能作为真实移动的验收证据。`controlled-replay.json` 为确定性回放；`native-smoke.json` 为原生输出尺寸、有限值及节点错误检查。

当前 24 项 Python 和 8 项 Node 测试通过，涵盖不同渲染频率下位移守恒、静止停止、手势失效取消、接管重置、采集时钟波动、限速时坐标连续性，以及摄像头调度和有界背压。原版本的五分钟和离线迁移验收见上级验证记录，不能当作本轮新构建重复完成的验收。
